## Critical (3)

### C1. SPEC compliance gap: warnings are dropped on success

- **Files:** `src/profile/importer.ts:215–240`, `src/persistence/schema.ts` (`profile_sources`)
- **Issue:** SPEC §13.4 says "Text-extraction **warnings or errors**" must be persisted. The schema
  has a single `textExtractionMessage` column. The `MarkdownExtractor` produces
  `warnings: string[]` (e.g., `markdown_contains_external_image_references`); the
  `ProfileImportService` returns them in `ImportedSource.warnings`, but they are
  **never written to the database**. A markdown CV with external image references produces
  a warning that is silently dropped after the import.
- **Recommendation:** Either (a) add a `warnings` JSON column to `profile_sources` and write the
  array; (b) add `textExtractionMessage`-style individual rows; or (c) document as a
  deliberate MVP deferral. Option (a) is the smallest change and keeps the existing
  `textExtractionMessage` column for backwards compatibility.
- **Status:** [ ] Open
- **Fix notes:**

### C2. Path-traversal edge case: basename `..` or `.`

- **Files:** `src/profile/file-copy.ts:9–27, 29–40`
- **Issue:** `path.basename()` correctly strips path separators on both POSIX and Windows, so
  `../../etc/passwd` → `passwd` (safe). But a user who controls the path on the command line
  could pass a path whose basename is literally `..` or `.`. The resulting
  `resolveSourceStoragePath` then returns `…/profile-sources/1/..` which `path.join` resolves
  to the parent directory `…/profile-sources/`. The copy would land in the wrong place and
  the `.tmp` rename would either fail or write to an unexpected location.
  - Verified: `path.basename('..')` returns `'..'`; `path.join('/data/profile-sources', '1', '..')` returns `/data/profile-sources`.
- **Recommendation:** Reject filenames whose `path.basename()` is `..` or `.`, or empty,
  with a clear `unsupported_format` error. Or, as defense-in-depth, validate the resolved
  destination is still inside `paths.profileSources.directory/{sourceId}/` after the join.
- **Status:** [ ] Open
- **Fix notes:**

### C3. `EncryptedPDFException` in the detector is dead code

- **Files:** `src/profile/extractors/pdf.ts:14–17`
- **Issue:** I added `EncryptedPDFException` to `ENCRYPTED_PDF_NAMES` but pdf-parse v2 only
  exports `PasswordException` (verified in
  `node_modules/pdf-parse/dist/pdf-parse/esm/Exception.js:41`). The `EncryptedPDFException`
  branch will never fire. The string-based fallback (`message.includes('encrypted')`) still
  works, but the explicit-name check is dead.
- **Recommendation:** Remove `EncryptedPDFException` from the set. Either keep
  `PasswordException` only, or keep the string fallback only. Both is redundant.
- **Status:** [ ] Open
- **Fix notes:**

## Important (9)

### I1. Redundant SHA-256 dedup lookup

- **Files:** `src/profile/importer.ts:142` + `src/persistence/repositories/profile-sources.ts:55`
- **Issue:** `ProfileImportService.importOne` calls `findBySha256` and short-circuits on hit.
  `ProfileSourceRepository.insert` **also** calls `findBySha256` and short-circuits on hit
  (lines 54–56). When the service calls `insert` after `findBySha256` returned null, the
  repository re-runs the same query. When the service's `findBySha256` returned non-null,
  the service never calls `insert` at all — so the repository's check is dead code in that
  path. The repository's check was added for "defense in depth" but is now redundant.
- **Recommendation:** Pick one location. Cleanest: remove the check from
  `ProfileSourceRepository.insert` (let the service own dedup) and document that `insert`
  is "INSERT OR ERROR" semantics. Alternatively, remove the service's pre-check and let
  the repository return the existing id. The second option is more robust against future
  callers.
- **Status:** [ ] Open
- **Fix notes:**

### I2. `reused` count semantics overlap with `extracted`/`failed`

- **Files:** `src/profile/importer.ts:115–120`, surfaced in `src/cli.ts:146–148`
- **Issue:** A reused source counts toward `reused` **and** `extracted` (or `failed`). So
  `extracted: 1, reused: 1` for a 1-source batch where the source was reused. The numbers
  overlap. A user can subtract, but it's not obvious. The JSON output mixes a "did the
  extraction succeed" count with a "was this a re-import" count without explanation.
- **Recommendation:** Either (a) document the semantics in JSDoc on `ProfileImportCounts`;
  (b) split into `newExtracted` + `reusedExtracted` and `newFailed` + `reusedFailed`;
  (c) keep `reused` as a separate "no new work" tag and make `extracted`/`failed` count only
  the **new** sources. Option (c) is cleanest. Option (a) is the smallest change.
- **Status:** [ ] Open
- **Fix notes:**

### I3. Test pattern: process.exit mock + exitOverride interaction is fragile

- **Files:** `tests/cli/profile-import.test.ts:30–34, 56–66, 73–90`
- **Issue:** The test patches `process.exit` globally. Commander's `exitOverride()` throws a
  `CommanderError` instead of calling `process.exit`. The test catches both (`__exit__:` from
  the mock, and `CommanderError` from `exitOverride`). If a future test fails synchronously
  between `beforeEach` (patch) and `afterEach` (restore), the patches leak into other tests.
  The catch block has correct logic but the structure is fragile.
- **Recommendation:** Wrap each test in a `try/finally` that restores the patches, or extract a
  helper `withMockedProcessExit(async () => { … })`. Lower priority — works today, just brittle.
- **Status:** [ ] Open
- **Fix notes:**

### I7. PDF bytes are read twice

- **Files:** `src/profile/importer.ts:139, 211`
- **Issue:** First, `createReadStream(absolutePath)` + `hashFileContents` streams the file for
  hashing. Then, after the copy, `fileSystem.readBytes(storedPath)` reads the entire file again
  for extraction. For a 10 MB CV this is one extra 10 MB buffer. The `ProfileImportService`
  could hash-while-copying via a stream pipeline to the destination, or extract from the
  buffer that was already read.
- **Recommendation:** Document as a known limitation or implement a streaming hash+copy+extract
  pipeline. Acceptable for MVP CVs (<5 MB).
- **Status:** [ ] Open
- **Fix notes:**

### I8. `text-pdf.pdf` content leaks into a real-world document

  displayed or printed in a debug context, the user sees placeholder text. More importantly,
  the extracted text `"Hello JobHunter\n\n"` is so short it doesn't exercise any interesting
  normalization (multi-line, blank-line collapse, etc.). A more realistic fixture would catch
  more real-world bugs.
- **Recommendation:** Acceptable for MVP. The test fixtures are documented as minimal.
- **Status:** [ ] Open / deferred — flag as deferred unless a richer fixture is desired.
- **Fix notes:**

### I9. `Image-only` PDF detection is heuristic

- **Files:** `src/profile/extractors/pdf.ts:6, 62, 92–97`
- **Issue:** The detection depends on pdf-parse returning whitespace-only text for image-only PDFs
  AND on the caller passing `pageJoiner: ''` to suppress the page-boundary marker
  (`-- 1 of 1 --`). If pdf-parse behavior changes or `pageJoiner: ''` is forgotten, the
  heuristic fails silently. There's no positive test for "PDF with mixed text+image but
  predominantly image".
- **Recommendation:** Add a comment in the file explaining the dependency, and add a unit test
  that asserts the `pageJoiner: ''` is passed.
- **Status:** [ ] Open
